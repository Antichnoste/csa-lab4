# csa_lab4

- ФИО: `Караганов Павел Эдуардович P3210`
- Вариант: `lisp | acc | harv | mc | tick | binary | stream | port | cstr | prob1 | pipeline`
  * `lisp` : Синтаксис языка Lisp. S-exp:
    1. Поддержка рекурсивных функций.
    2. Любое выражение (statement) - expression.
  * `acc` : Система команд должна быть выстроена вокруг аккумулятора:
    1. Инструкции - изменяют значение, хранимое в аккумуляторе.
    2. Ввод-вывод осуществляется через аккумулятор.
  * `harv` : Гарвардская архитектура.
  * `mc` : Команды реализованы с помощью микрокоманд.
  * `tick` : Процессор необходимо моделировать с точностью до такта, процесс моделирования может быть приостановлен на любом такте.
  * `binary` : Бинарное представление машинного кода.
  * `stream` : Ввод-вывод осуществляется как поток токенов.
  * `port` : Port-mapped (специальные инструкции для ввода-вывода).
  * `cstr` : Null-terminated (C string).
  * `prob1` : Euler problem 4 [link](https://projecteuler.net/problem=4).
  * `pipeline` : Конвейерная организация работы процессора:
    * Количество стадий конвейера - не менее 3.

## Язык Lisp

Синтаксис основан на S-выражениях (S-exp). Каждая конструкция записывается в виде списка в круглых скобках и возвращает значение. Транслятор осуществляет построение Абстрактного Синтаксического Дерева (AST) для дальнейшего анализа и генерации кода.

### Формальная грамматика (EBNF)

```ebnf
<program> ::= <expression_list>

<expression_list> ::= <expression> | <expression> <expression_list>

<expression> ::= <number>
               | <string>
               | <identifier>
               | "(" <special_form> ")"
               | "(" <function_call> ")"

<special_form> ::= <var_declaration>
                 | <set_assignment>
                 | <if_expression>
                 | <loop_expression>
                 | <return_expression>
                 | <defun_declaration>
                 | <print_op>
                 | <io_op>
                 | <mem_op>
                 | <binop_expression>

<var_declaration> ::= "defvar" <identifier> [ <expression> ]

<set_assignment> ::= "setq" <identifier> <expression>

<if_expression> ::= "if" <expression> <expression> [ <expression> ]

<loop_expression> ::= "loop" <expression_list>

<return_expression> ::= "return" <expression>

<defun_declaration> ::= "defun" <identifier> "(" <parameter_list> ")" <expression_list>

<function_call> ::= <identifier> <argument_list>

<print_op> ::= "print" <expression>

<io_op> ::= "in" <number> 
          | "out" <number> <expression>

<mem_op> ::= "read-mem" <expression> 
           | "write-mem" <expression> <expression>

<binop_expression> ::= <operator> <expression> <expression> <optional_expr_list>

<optional_expr_list> ::= "" | <expression> <optional_expr_list>

<operator> ::= "+" | "-" | "*" | "/" | "mod" | "=" | "!=" | "<" | ">"

<parameter_list> ::= "" | <identifier> <parameter_list>

<argument_list> ::= "" | <expression> <argument_list>

<identifier> ::= <letter> | <letter> <identifier_tail>

<identifier_tail> ::= <letter> | <digit> | "_" | "-" | <identifier_tail>

<string> ::= "\"" <string_content> "\""

<string_content> ::= "" | <character> <string_content>

<character> ::= <letter> | <digit> | " " | "," | "!" | "?" | "\n" | ...

<letter> ::= "a" | "b" | ... | "z" | "A" | "B" | ... | "Z"

<digit> ::= "0" | "1" | ... | "9"

<number> ::= ["-" | "+"] <digit> | ["-" | "+"] <digit> <number>
```

### Семантика

*   **Statement = Expression:** Любая языковая конструкция, включая `if`, `setq` и `loop`, вычисляется и оставляет итоговый результат в аккумуляторе (`ACC`). Это позволяет использовать конструкции вложенно, формируя сложные цепочки вычислений. Пример: `(setq x (if (= y 0) 1 2))`.
*   **Стратегия вычислений (аппликативный порядок):** Строгая. Все аргументы функций и бинарных операторов полностью вычисляются слева направо перед выполнением самой операции. 
*   **Переменное число аргументов:** Бинарные математические и логические операторы поддерживают левую свертку неограниченного числа аргументов. Транслятор аппаратно разворачивает выражение вида `(+ 1 2 3 4)` в `(+ (+ (+ 1 2) 3) 4)` на этапе построения AST.
*   **Типизация:** Динамическая / бестиповая на уровне синтаксиса. Все данные обрабатываются процессором как 32-битные знаковые целые числа.
*   **Области видимости и контекст вычислений:**
    *   **Глобальная:** Переменные (`defvar`) выделяются статически (начиная с адреса `0x1000`).
    *   **Локальная:** Аргументы функций живут на стеке. Доступ к ним осуществляется через относительную адресацию.
*   **Строки (Null-terminated - `cstr`):** Записываются в двойных кавычках. При трансляции посимвольно размещаются в статической памяти данных (один символ = одно 32-битное слово), завершаясь нулевым байтом `\0`.
*   **Ввод-вывод (Port-mapped):** Осуществляется в виде потока токенов через встроенные низкоуровневые операторы (in <port>) и (out <port> <val>). На аппаратном уровне в процессоре реализован строгий дешифратор портов: порт 0 аппаратно привязан к контроллеру ввода (чтение токена), а порт 1 — к контроллеру вывода. Обращения к иным портам игнорируются железом. Для соблюдения аппаратного контракта (ABI) компилятор автоматически транслирует высокоуровневую функцию print в OUT IMMEDIATE 1.

## Организация памяти

* Модель: **Гарвардская архитектура** (память инструкций и память данных физически разделены). 
* Тип памяти: Однопортовая для каждого модуля. 
* Машинное слово: 32 бита.

```text
       Instruction Memory (IMEM)
+----------------------------------------+
| 0x0000 : JMP _start                    | <- Точка входа
| 0x0001 : ...                           | 
| ...                                    |
| 0x002A : _start: LD #1                 | <- Скомпилированные инструкции
| 0x002B : CALL solve                    | 
| ...                                    |
+----------------------------------------+

        Data Memory (DMEM)
+----------------------------------------+
| 0x0000 : 72  ('H')                     | \
| 0x0001 : 105 ('i')                     | | <- 1. Статические данные (0x0000 - 0x0FFF).
| 0x0002 : 0   ('\0')                    | |    Здесь лежат нуль-терминированные строки (cstr)
| ...                                    | /
|----------------------------------------|
| 0x1000 : scratch_ret (system)          | \
| 0x1001 : scratch_ptr (system)          | | <- 2. Системные переменные компилятора.
| 0x1002 : variable_sum                  | | <- 3. Глобальные переменные (0x1002 - 0x7FFF).
| 0x1003 : variable_i                    | |    Определяются через (defvar ...)
| ...                                    | /    
|----------------------------------------|
|                  ...                   |
|           (Свободная память)           |
|                  ...                   |
|----------------------------------------|
| 0xFFFD : local_var_temp                | \ 
| 0xFFFE : arg_limit                     | | <- 4. Стек вызовов (растет вверх, к 0x1000).
| 0xFFFF : ret_addr_main                 | |    Вершина стека указывается регистром SP.
+----------------------------------------+
```

### Механика отображения программы на процессор:
1. **Инструкции:** Компилятор генерирует последовательность 32-битных машинных слов и загружает их в `Instruction Memory`. Процессор выполняет их линейно, запрашивая по адресу из регистра `PC`.
2. **Строки (`cstr`):** При обнаружении строкового литерала (например, `"Hi"`), компилятор посимвольно сохраняет его в статический сегмент памяти данных, завершая нулем (`\0`). В коде инструкции вместо самой строки используется адрес первого символа (`0x0000`). Из-за упрощения модели, один 8-битный символ занимает целое 32-битное машинное слово.
3. **Глобальные переменные:** Размещаются, начиная с адреса 0x1002. Ячейки 0x1000 и 0x1001 жестко зарезервированы компилятором под системные нужды (scratch_ret для сохранения ответа функции при очистке стека и scratch_ptr для косвенной адресации строк). Транслятор заменяет имена переменных на их фиксированные физические адреса.
4. **Локальные переменные и рекурсия:** Размещаются динамически на стеке (начиная с `0xFFFF` и двигаясь в сторону уменьшения адресов). Доступ к ним осуществляется через относительное смещение от текущего значения регистра `SP` (Stack Pointer). При вызове функции на стек сохраняется адрес возврата.

## Система команд

### Особенности процессора
- **Аккумуляторная архитектура (`acc`):** Основным операндом всех АЛУ-операций является регистр `ACC`. Второй операнд берется либо из инструкции (Immediate), либо из памяти данных.
- **Портовый ввод-вывод (`port`):** Выделенное адресное пространство портов, доступное через специальные команды `IN` и `OUT`.
- **Конвейер (`pipeline`):** 3 стадии (Instruction Fetch, Instruction Decode / Operand Fetch, Execute / Memory / Write-Back).

### Набор инструкций

| Мнемоника | Операнд | Описание | Тактов* |
|:---|:---|:---|:---|
| **Загрузка/Запись** | | | |
| `LD` | `addr` | `ACC <- DMEM[addr]` | 1 |
| `LD` | `#val` | `ACC <- val` | 1 |
| `LD` | `[addr]` | `ACC <- DMEM[DMEM[addr]]` | 2 (stall) |
| `ST` | `addr` | `DMEM[addr] <- ACC` | 1 |
| `ST` | `[addr]` | `DMEM[DMEM[addr]] <- ACC` | 2 (stall) |
| **Арифметика** | | | |
| `ADD` | `addr/#val` | `ACC <- ACC + operand` | 1 |
| `SUB` | `addr/#val` | `ACC <- ACC - operand` | 1 |
| `MUL` | `addr/#val` | `ACC <- ACC * operand` | 1 |
| `DIV` | `addr/#val` | `ACC <- ACC / operand` | 1 |
| `MOD` | `addr/#val` | `ACC <- ACC % operand` | 1 |
| `CMP` | `addr/#val` | Выставить флаги на основе `ACC - operand` | 1 |
| **Управление** | | | |
| `JMP` | `addr` | `PC <- addr` | 1 (flush) |
| `JZ` | `addr` | Переход, если флаг `Z = 1` | 1 (flush**) |
| `JNZ` | `addr` | Переход, если флаг `Z = 0` | 1 (flush**) |
| `JLT` | `addr` | Переход, если флаг `N = 1` | 1 (flush**) |
| `JGT` | `addr` | Переход, если `Z=0` и `N=0` (результат больше 0) | 1 (flush**) |
| **Стек и Функции** | | | |
| `PUSH` | - | `DMEM[SP] <- ACC; SP <- SP - 1` | 2 (stall) |
| `POP` | - | `SP <- SP + 1; ACC <- DMEM[SP]` | 2 (stall) |
| `CALL` | `addr` | `PUSH PC; PC <- addr` | 2 (stall/flush) |
| `RET` | - | `POP PC` | 2 (stall/flush) |
| **Ввод-Вывод** | | | |
| `IN` | `port` | `ACC <- PORT[port]` | 1 |
| `OUT` | `port` | `PORT[port] <- ACC` | 1 |
| `HALT` | - | Остановка процессора | 1 |


### Пояснения:

*   **`* Тактов`**: Указано количество тактов на исполнение одной стадии инструкции. Благодаря конвейеру, в идеальном случае (линейный код) процессор завершает одну инструкцию за каждый такт.
*   **`stall`**: Команды со стеком (`PUSH`/`POP`) и косвенная адресация (`LD [addr]`) требуют двух обращений к памяти или сложных манипуляций с регистрами. Микрокод в этих случаях приостанавливает стадию выборки (IF), пока стадия выполнения (EX) завершает операцию.
*   **`flush`**: При выполнении перехода инструкции, которые уже попали в конвейер (стадии IF и ID), становятся невалидными. Процессор очищает конвейер и начинает выборку с нового адреса `PC`.
*   **`flush**`**: Для условных переходов сброс происходит только в том случае, если условие выполнилось (переход совершен).

### Кодирование инструкций

**Бинарное представление (`binary`)**: Машинное слово — 32 бита.
```text
┌─────────┬───────┬───────────────────────────────────────────────────────┐
│ 31...24 │ 23 23 | 21                       ...                        0 │
├─────────┼───────┼───────────────────────────────────────────────────────┤
│  Opcode │  Mode |            адрес памяти / значение (операнд)          │
└─────────┴───────┴───────────────────────────────────────────────────────┘
   (8 бит)  (2 бит)                      (22 бита)
```

1.  **Opcode (8 бит, 31–24):** Код операции. Определяет основное действие инструкции. Всего доступно 256 кодов.
2.  **Addressing Mode (2 бита, 23–22):** Определяет, как интерпретировать поле аргумента. Это критически важно для работы с переменными и стеком.
3.  **Argument / Address (22 бита, 21–0):** Содержит числовое значение, адрес памяти или смещение. Поддерживает знаковые значения в режиме `Immediate`.

### Режимы адресации (`Mode`)

| Биты | Режим | Описание | Применение |
|:---:|:---|:---|:---|
| **00** | **Immediate** | Операнд находится прямо в инструкции. | Загрузка констант, арифметика с числами (`LD #10`). |
| **01** | **Direct** | В поле аргумента — абсолютный адрес в DMEM. | Глобальные переменные (`defvar`). |
| **10** | **Indirect** | В аргументе адрес ячейки, где лежит целевой адрес. | Работа с указателями и строками (`cstr`). |
| **11** | **Relative** | Адрес вычисляется как `SP + Argument`. | Доступ к локальным переменным и аргументам функций на стеке. |

Команда: `LD #42` (Загрузить константу 42 в аккумулятор)

*   `Mode`: `Immediate` = `0x0` (`00` bin)
*   `Argument`: `42` (`0000000000000000101010` bin)

## Транслятор

Интерфейс командной строки: `python translator.py <input.lisp> <target.bin> [target.asm]`

Реализация транслятора разделена на три логических этапа (прохода), что обеспечивает независимость синтаксического разбора от генерации машинного кода.

### Этапы трансляции:

1.  **Синтаксический анализ:**
    *   Текст программы разбивается на токены.
    *   Построение **AST (Abstract Syntax Tree)** в виде вложенных списков. На этом этапе проверяется парность скобок и корректность структуры S-выражений.
2.  **Анализ семантики:**
    *   **Регистрация символов:** Формируется таблица имен (глобальные переменные и функции).
    *   **Работа со строками (`cstr`):** Все строковые литералы выносятся в статическую секцию данных. Транслятор заменяет строку в коде на её будущий адрес в памяти.
    *   **Анализ областей видимости:** Для локальных переменных вычисляются смещения относительно указателя стека (`SP`).
3.  **Генерация кода:**
    *   **Обход дерева в глубину:** Рекурсивная генерация последовательности команд.
    *   **Решение ограничений `acc`:** Так как в аккумуляторной архитектуре только один регистр для данных, при вычислении вложенных выражений транслятор генерирует неявные команды `PUSH` и `POP` для сохранения промежуточных результатов на стеке.
    *   **Label Resolution:** Замена символических меток (имен функций, адресов переходов в `if` и `loop`) на конкретные адреса в памяти инструкций.

### Структура бинарного файла

Результатом работы является файл, состоящий из 32-битных слов:
*   **Заголовок:** количество инструкций (N) и количество слов данных (M).
*   **Секция инструкций:** Последовательность команд в формате `Opcode[8] | Mode[2] | Arg[22]`.
*   **Секция данных:** Инициализированные значения статических строк и глобальных переменных, которые загружаются в DMEM при старте модели.

**Пример бинарного файла (hello_user.bin, первые 64 байта, big-endian):**

```text
0000: 00 00 00 21 00 00 10 04 20 40 00 01 01 40 10 01
0010: 02 40 10 03 01 80 10 03 15 00 00 00 21 40 00 0B
0020: 41 00 00 00 01 40 10 03 10 00 00 01 02 40 10 03
0030: 20 40 00 03 01 40 10 03 40 00 00 00
```

Расшифровка:
* `00 00 00 21` = 33 инструкции
* `00 00 10 04` = 4100 слов данных (включая паддинг до `0x1000` и глобальные переменные)
* Первые инструкции: `0x20400001` (JMP 1), `0x01401001` (LD 0x1001), `0x02401003` (ST 0x1003)

**Пример кодирования:**

Команда: `LD #42`

* `Opcode = 0x01` (LD)
* `Mode = 00` (Immediate)
* `Arg = 42` (`0x00002A`)

Формула: `word = (Opcode << 24) | (Mode << 22) | (Arg & 0x3FFFFF)`

Результат: `0x0100002A`

**Пример расшифровки:**

Слово: `0x2140000A`

* `Opcode = (word >> 24) & 0xFF = 0x21` → `JZ`
* `Mode = (word >> 22) & 0x3 = 0b01` → `Direct`
* `Arg = word & 0x3FFFFF = 0x00000A` → адрес `10`

Для знакового 22-битного аргумента: если установлен бит `21`, то `Arg = Arg - (1 << 22)`.

### Конвейер (Pipeline)

Реализован 3-стадийный конвейер. Разделение стадий обеспечивается регистрами-защелками (Latches).
1. **IF (Instruction Fetch):** Выборка инструкции из памяти программ (`IMEM`) по адресу из регистра `PC` (счетчик аппаратно инкрементируется на `+1`). Инструкция защелкивается в регистр `IF/ID`.
2. **ID (Instruction Decode & Operand Fetch):** Аппаратный сплиттер разделяет 32-битное машинное слово из защелки `IF/ID` на логические шины: `Opcode`, `Mode` и `Arg` (Immediate/Addr). Оригинальный адрес команды (`PC`) пробрасывается транзитом для сохранения контекста `CALL`. Это состояние процессора защелкивается в `ID/EX Latch`.
3. **EX (Execute / Memory / Write-Back):** Стадия полностью управляется микропрограммным автоматом (CU). Для исключения конфликтов по данным (Data Hazards) при заморозке конвейера, архитектурные регистры `ACC` и `SP` физически размещены на стадии EX и читаются напрямую в обход межкаскадных защелок. Микрокод потактово управляет мультиплексорами, выполнением операций в `ALU`, доступом к `DMEM` и регистрам. Флаги `Z` и `N` от АЛУ отправляются обратно в CU для вычисления условий ветвления.

**Обработка конфликтов конвейера:**
- **Условные переходы (Flush):** При вычислении успешного перехода (`JMP`, `CALL`, `JZ` и т.д.) микрокод на стадии EX принудительно изменяет регистр `PC` и генерирует сигнал `FLUSH`. Содержимое защелок `IF/ID` и `ID/EX` очищается, чтобы предотвратить исполнение ошибочно выбранных по старому пути инструкций.
- **Многотактовые операции (Stall):** При работе со стеком, памятью (косвенная адресация) и подпрограммами микропрограмма длится несколько тактов. Микрокод генерирует сигнал `STALL`, который аппаратно блокирует обновление защелок `IF/ID` и `ID/EX` и регистра `PC`, "замораживая" предыдущие стадии до завершения текущей макрокоманды.

**Пример потактового выполнения (hello_user.bin, `--trace`):**

* Вход: `name.txt = Alice`

### DataPath

![DataPath](img/DataPath.png)

Тракт данных представляет собой строгую аппаратную реализацию 3-стадийного конвейера.

- **Память:** Реализована Гарвардская архитектура. Независимые `IMEM` (память инструкций) и `DMEM` (память данных).
- **Стадии конвейера и Защелки (Latches):**
  - **IF / ID Latch:** Разделяет стадию выборки от декодирования.
  - **Instruction Decoder:** Аппаратный сплиттер на стадии ID. Разделяет 32-битное машинное слово на шины `Opcode [31:24]`, `Mode [23:22]` и `Arg [21:0]`.
  - **ID / EX Latch:** Сохраняет состояние процессора для автономной работы стадии EX. Фиксирует операнды, а также пробрасывает транзитом значение регистра `PC`.
- **Регистры:**
  - **PC (Program Counter):** Имеет собственный выделенный комбинационный инкрементор `+1` для независимой работы на стадии IF.
  - **SP (Stack Pointer):** Синхронный реверсивный счетчик (`+/- 1`), аппаратно управляемый сигналами `Inc/Dec`.
  - **ACC (Accumulator):** Основной регистр. Жестко привязан к левому входу АЛУ.
  - **BR (Buffer Register):** Вспомогательный теневой регистр. Защелкивает промежуточный адрес-указатель на первом такте при косвенной (`INDIRECT`) адресации.
- **Мультиплексоры (MUX) и маршрутизация:**
  - **ADDR ADDER:** Выделенный сумматор адреса, непрерывно вычисляющий эффективный адрес `SP + Offset`.
  - **MUX Addr [20:19]:** Выбирает итоговый адрес для `DMEM` из 4 источников: `Inst Addr` (Direct), `SP+Offs` (Relative), чистый `SP` (работа со стеком) или `Indirect` (из регистра BR).
  - **MUX Data [16]:** Выбирает, что записать в `DMEM`: данные из `ACC` (обычное сохранение) или адрес возврата `PC+1` (сохранение контекста при `CALL`).
  - **MUX Src B [18:17]:** Выбирает правый операнд АЛУ: константу `Immediate`, данные из `DMEM` или токен из `IN Port`.
  - **MUX PC:** Выбирает источник для счетчика команд: обычный инкремент `+1` или адрес прыжка с шины `ALU Out / Branch Target` (все прыжки маршрутизируются транзитом через АЛУ).
- **ALU (АЛУ):** Выполняет операции над `ACC` и выбранным правым операндом. Генерирует флаги `Z` и `N` для модуля условий.

### Control Unit

![Control Unit](img/CU.png)

В связи со сложностью совмещения конвейера (`pipeline`) и микрокода (`mc`), в процессоре реализовано **гибридное распределенное управление**. Стадии IF и ID управляются жестко зашитой логикой (Hardwired), так как их поведение тривиально. Control Unit (микропрограммный автомат) физически обслуживает только самую сложную стадию исполнения (EX).

**Принцип работы:**
1. 10 бит (`Opcode` + `Mode`) из защелки `ID/EX` поступают в комбинационный **Address Mapper**, который мгновенно транслирует их в стартовый 6-битный адрес микропрограммы.
2. В начале исполнения инструкции **Micro-PC** защелкивает этот стартовый адрес.
3. Из **Micro-ROM** (плоского массива ПЗУ) выгружается 26-битное микрослово.
4. Микрослово попадает в **Control Signal Decoder**, где расплетается на физические управляющие провода (управление защелками, мультиплексорами, АЛУ и памятью), которые мгновенно применяются к DataPath.
5. Для условных переходов биты `Cond Code` отправляются в **Condition Module**, где сверяются с реальными флагами АЛУ (`Z`, `N`). При совпадении генерируется сигнал разрешения перезаписи `PC`.
6. Если инструкция многотактовая (например, `PUSH` или косвенная адресация), микрокод выдает сигнал `STALL`. Это замораживает защелки IF/ID и ID/EX, пока `Micro-PC` переходит по адресу из поля `Next Addr` для выполнения следующих шагов. После завершения микропрограммы `uPC` сбрасывается в `0` (FETCH), и конвейер оживает.

**Формат микрокоманды (26 бит):**

| Биты | Сигнал | Описание |
|:---:|:---|:---|
| **25:24** | `Latch Ctrl` | Управление защелками конвейера (0: Normal, 1: STALL, 2: FLUSH). |
| **23:21** | `ALU Op` | Операция АЛУ (вкл. PASS B для транзита операндов и PASS A для вывода). |
| **20:19** | `MUX A` | Адрес для `DMEM` (0: Inst Addr, 1: SP+Offs, 2: BR/Indirect, 3: Pure SP). |
| **18:17** | `MUX B` | Правый операнд АЛУ (0: Immediate, 1: DMEM Data, 2: IN Port). |
| **16**    | `MUX DATA` | Данные для `DMEM` (0: ACC, 1: PC+1 [адрес возврата для CALL]). |
| **15:13** | `Mem/Port`| Сигналы внешних шин (Чтение/Запись `DMEM`, Чтение `IN`, Запись `OUT`). |
| **12:10** | `Reg En` | Дешифратор записи в регистры (ACC WE, SP INC/DEC, PC WE). Поддерживает совмещенные команды (например, PC WE + SP DEC для `CALL`). |
| **9:6**   | `Cond` | Код условия для переходов (NONE, JZ, JNZ, JLT, JGT). |
| **5:0**   | `Next Addr` | Адрес следующей микрокоманды в Micro-ROM (0 = завершение). |

## Тестирование

Тестирование выполняется через golden test-ы. Каждый тест берет соответствующий файл из `test/*.yml`,
собирает одноименный пример из `lisp/<name>/<name>.lisp`, затем сравнивает полученные `target.asm` и `out_log`
с эталоном из YAML.

### Что проверяют тесты

1. `cat.lisp` — чтение ASCII-символов из потока ввода и повторный вывод через порт.
2. `hello.lisp` — печать статической строки `cstr`.
3. `hello_user.lisp` — чтение имени, запись символов в память и вывод приветствия.
4. `double_precision.lisp` — арифметика с плавающей точностью в рамках модели проекта.
5. `prob1.lisp` — рекурсивное решение Euler 4, математика, стек и возвраты.
6. `sort.lisp` — сортировка строки как массива ASCII-символов.
7. `tail_recursion.lisp` — хвостовая рекурсия и работа стека.
8. `expressions.lisp` — проверка правильности обработки вложенных выражений и работы с аккумулятором.

Для CI настроен GitHub Actions workflow: устанавливает `pytest` и `pytest-golden`, затем прогоняет `test_golden.py`. Отдельный шаг линтера в workflow не подключен.

### Как запускать

Запустить все golden-тесты:
```bash
pytest test_golden.py
```

Запустить только один тест:
```bash
pytest test_golden.py -k hello_user
```

При обновлении эталонов:
```bash
pytest test_golden.py --update-goldens
```

Пример вывода симулятора (`--trace`):
